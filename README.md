# BakedBoston

BakedBoston is a community logistics platform connecting bakery surplus,
volunteer drivers, and nearby food pantries.

The repository now contains two product surfaces:

- `app/`: the web application and administrator workspace deployed on Vercel
- `mobile/`: the native Expo/React Native app for drivers, bakeries, and
  pantries

The mobile app includes driver registration and identity verification, live
route browsing and reservations, delivery progress, partner workspaces,
notifications, and impact tracking.

## Live optimization

Production matching is delegated to the separate `bakedboston-optimizer`
service. It builds a Gurobi mixed-integer model over active driver requests,
confirmed bakery pickups, and eligible pantry windows. One normalized
acceptance-adjusted expected-impact objective balances pantry coverage, raw and
saved-food volume/evenness, opportunity priority, net direct CO₂e benefit, and
driver fit. Each driver and bakery
pickup can be assigned at most once, while open pantries may receive multiple
deliveries.

For one driver, the public explanation writes the same objective compactly as

```text
r★ = arg max { πᵣ · (ωᵀφᵣ) | r ∈ ℛ(d) }
```

Here `ℛ(d)` is the hard-feasible route set, `πᵣ` is modeled completion
likelihood, `ω = (10,10,10,10,10,10,20,20)ᵀ` is the policy-weight vector, and
`φᵣ = (κᵣ, νᵣʳᵃʷ, εᵣʳᵃʷ, νᵣˢᵃᵛᵉᵈ, εᵣˢᵃᵛᵉᵈ, ρᵣ, γᵣ, χᵣ)ᵀ` contains pantry
coverage, raw volume/evenness, saved volume/evenness, pantry priority, direct
environmental benefit, and driver fit. This is a notation change only; the
implemented objective, weights, and constraints are unchanged.

See [`docs/optimizer-integration.md`](docs/optimizer-integration.md) for the
service contract, environment variables, licensing boundary, and production
verification checklist.

## Academic routing simulator

The public [five-day simulator](https://www.baked-boston.com/simulator) replays
a deterministic, synthetic experiment generated by the optimizer repository.
Visitors can choose a day, open a decision time, switch among simultaneous
drivers, and inspect every route recommended to that driver in score order.
After the joint Gurobi solve resolves bakery conflicts, the selected route is
always rank #1—the highest-scoring route in the conflict-free list shown to
that driver.

The page documents the complete objective—including why modeled acceptance
scales impact instead of imposing a 99%-of-best cutoff—and reports route food saved as bakery
food × bakery usability × pantry distribution. It tracks bakery food not picked
up and collected food not ultimately distributed. Fixed institution inputs and
environmental coefficients live with the optimizer source in
[`docs/institutions.md`](https://github.com/vapeyproductions/bakedboston-optimizer/blob/main/docs/institutions.md)
instead of being duplicated on the website. The comparison panels evaluate
BakedBoston, Nair distance-first, Xue–Zou Total-Curb, and Horner stochastic-menu
policies on the same seeded scenario. The simulator does not create or change
live organization records. The saved walkthrough uses illustrative seed 2033.
Its comparison begins with a six-pillar Balanced Total Impact index covering
completed service, food recovery, net environmental benefit, distribution
equity, volunteer fit, and route efficiency. The index is a scenario-relative
communication aid rather than an optimizer input; the detailed physical and
fairness metrics remain available in an expandable audit section.

The homepage also provides a read-only one-driver trace over the current
registered, active, address-validated partner network. Its reproducible
synthetic request clock is selected to expose a useful mix of feasible and
rejected bakery–pantry pairs without changing any institution schedule. A
filter audit shows the first failed hard rule for each rejected pair before the
surviving route columns are compared by acceptance-adjusted expected impact.

## Workspace Auth Headers

OpenAI workspace sites can read the current user's email from
`oai-authenticated-user-email`.

SIWC-authenticated workspace sites may also receive
`oai-authenticated-user-full-name` when the user's SIWC profile has a non-empty
`name` claim. The full-name value is percent-encoded UTF-8 and is accompanied by
`oai-authenticated-user-full-name-encoding: percent-encoded-utf-8`.

Treat the full name as optional and fall back to email when it is absent:

```tsx
import { headers } from "next/headers";

export default async function Home() {
  const requestHeaders = await headers();
  const email = requestHeaders.get("oai-authenticated-user-email");
  const encodedFullName = requestHeaders.get("oai-authenticated-user-full-name");
  const fullName =
    encodedFullName &&
    requestHeaders.get("oai-authenticated-user-full-name-encoding") ===
      "percent-encoded-utf-8"
      ? decodeURIComponent(encodedFullName)
      : null;

  const displayName = fullName ?? email;
  // ...
}
```

## Optional Dispatch-Owned ChatGPT Sign-In

Import the ready-to-use helpers from `app/chatgpt-auth.ts` when the site needs
optional or required ChatGPT sign-in:

- Use `getChatGPTUser()` for optional signed-in UI.
- Use `requireChatGPTUser(returnTo)` for server-rendered pages that should send
  anonymous visitors through Sign in with ChatGPT.
- Use `chatGPTSignInPath(returnTo)` and `chatGPTSignOutPath(returnTo)` for
  browser links or actions.
- Pass a same-origin relative `returnTo` path for the destination after sign-in
  or sign-out. The helper validates and safely encodes it.
- Mark protected pages with `export const dynamic = "force-dynamic"` because
  they depend on per-request identity headers.

Dispatch owns `/signin-with-chatgpt`, `/signout-with-chatgpt`, `/callback`, the
OAuth cookies, and identity header injection. Do not implement app routes for
those reserved paths. Routes that do not import and call the helper remain
anonymous-compatible.

SIWC establishes identity only; it does not prove workspace membership. Use the
Sites hosting platform's access policy controls for workspace-wide restrictions,
or enforce explicit server-side membership or allowlist checks.

Use SIWC for account pages, user-specific dashboards, saved records, and write
actions tied to the current ChatGPT user. Leave public content anonymous.
